# 空選択時の変身仮選択取消

根拠: Planning/ゲーム全体仕様.md §3「カード選択を末尾からすべて外し、さらにキャンセルすると変身選択を取り消す」。対象は今回の未確定変身のみ。前ターンから継続する変身は任意解除せず、別の仮選択を取り消したら元の変身と画面開始時の残回数へ戻す。§6の加工Undoとは別操作。

実装: ICustomScreenView.BindTransformationsで現在のモデルを接続し、通常BattleController/DungeonBattleControllerが共用するBattleSessionController.Attachで設定、Detachで解除する。CustomScreenViewの取消は選択カードがあれば末尾1枚、入力時点で空なら既存TryCancelPendingを呼ぶ。1入力で最後のカードと仮選択を同時に消さない。Initializeの描画準備が後から完了してもセッションの接続を上書きしない。

優先順位: 加工モード中は既存の加工モード入力へ委譲。通常モードの既存Space→Enter→取消の順は維持し、確定後は取消しない。時刻付き入力の同一論理フレーム内連打は1回へ併合し、翌フレームに持ち越さない。通常ポーズ中の入力を保留して再開後に実行しない。

検証: 実View・共通Controllerセッションで30/60/120fps、追いつき、戦闘開始チェックポイント復帰の8ケースを更新。実Input SystemでESC連打、仮選択なし、ポーズ・確定後、継続変身/残回数/耐性復元、使用済み管理、ゲージ維持を検証。ゲーム操作のリマップ適用後も同じ経路を検証。再Attach/Detachで取消対象を交換・解除し、加工済みカードの取消と仮選択取消では加工履歴・コストを維持、明示Undoだけで素材/手札順/コストを戻す。全Unity MCP EditMode回帰を実行。

リマップの実範囲: 現行のリマップ対象はゲーム操作スロットのみ。取消は既存固定ESC。今回検証するのは既存ゲーム操作リマップとの共存であり、取消キー自体のリマップ対応ではない。メニューの必須割当・設定保存・ガイド更新の製品接続は別の残件。

未実装: 製品の変身一覧/選択UI、変身ごとのカード変化対象・変化先・手札上限増分、変身由来加工の巻戻し、追加ドロー復元。今回用いるテスト用変身定義は製品データに追加しない。既存加工を仮選択に由来するとみなして無条件に戻す処理も追加しない。保存は戦闘開始チェックポイントであり、カスタム画面途中の新しい保存は設けない。描画VM同期・build・実機確認なし。
